# Лабораторна робота №6 — Quartz Scheduler


## Мета роботи


Додати до Helpdesk System завдання, які запускаються автоматично за розкладом. Розклад має зберігатися в PostgreSQL, щоб не зникати після перезапуску застосунку.


## Що таке Quartz


**Quartz** — бібліотека-планувальник для Java. Вона запускає потрібний код за розкладом: наприклад, щодня формує звіт або перевіряє наявність тікетів, які довго залишаються без виконавця.


У Quartz є кілька ключових понять:



- **Job** — клас із кодом, який потрібно виконати.

- **JobDetail** — опис завдання: його клас, унікальна назва, група та параметри за замовчуванням.

- **Trigger** — правило запуску завдання. Наприклад, Cron-вираз може означати «щодня о 09:00».

- **JobDataMap** — мапа параметрів, які доступні завданню під час виконання.



Quartz може зберігати завдання лише в пам’яті, але тоді після перезапуску застосунку його розклад буде втрачено. У цій роботі використовується **JDBC JobStore**: Quartz зберігає розклад і стан у таблицях `QRTZ_*` бази даних. Це не бізнес-таблиці Helpdesk — самі тікети, користувачі та інші дані зберігаються окремо.


## Підключення та зберігання розкладу


Для інтеграції додається залежність `spring-boot-starter-quartz`. Spring Boot підключає Quartz до застосунку, а конфігурація в `application.properties` вказує, що потрібно використовувати JDBC JobStore:


Properties






```
spring.quartz.job-store-type=jdbc
spring.quartz.jdbc.initialize-schema=never
spring.quartz.properties.org.quartz.scheduler.instanceName=HelpdeskScheduler
spring.quartz.properties.org.quartz.scheduler.instanceId=AUTO
spring.quartz.properties.org.quartz.jobStore.driverDelegateClass=org.quartz.impl.jdbcjobstore.PostgreSQLDelegate
spring.quartz.properties.org.quartz.jobStore.tablePrefix=QRTZ_
spring.quartz.overwrite-existing-jobs=true

```





`job-store-type=jdbc` вмикає збереження стану Quartz у базі даних. `driverDelegateClass` задає Quartz обробник, сумісний із PostgreSQL, а `tablePrefix` визначає префікс таблиць планувальника.


`initialize-schema=never` вимикає автоматичне створення таблиць Quartz засобами Spring Boot. Схемою керує Liquibase: для цього додається окремий changeset із таблицями `QRTZ_*` та потрібними індексами, а його файл підключається в `db.changelog-master.yaml`. Так створення схеми відбувається разом з іншими міграціями проєкту.


Назва планувальника `HelpdeskScheduler` має збігатися зі значенням `SCHED_NAME`, використаним у початкових записах таблиці `QRTZ_LOCKS`. `instanceId=AUTO` дає екземпляру планувальника автоматично визначений ідентифікатор.


## Реалізовані завдання


У роботі передбачені два завдання:



1. `DailyTicketSummaryJob` формує короткий звіт про кількість тікетів у статусах `NEW`, `IN_PROGRESS`, `RESOLVED` і `CLOSED`.

2. `UnassignedTicketReminderJob` перевіряє кількість нових тікетів, які не мають виконавця та старші за задану кількість годин.



Бізнес-логіка знаходиться в `ScheduledTicketTasksServiceImpl`, а класи Job лише зчитують параметри й викликають метод сервісу. Так Job не містить запитів до репозиторію та окремої бізнес-логіки.


Наприклад, завдання нагадування отримує параметр із об’єднаної мапи Quartz і делегує перевірку сервісу:


Java






```
int minimumAgeHours =
        context.getMergedJobDataMap().getInt("minimumAgeHours");

scheduledTicketTasksService.logUnassignedTicketReminder(minimumAgeHours);

```





Сервіс обчислює граничний час і передає його до репозиторію, який рахує потрібні тікети:


Java






```
LocalDateTime cutoff = LocalDateTime.now().minusHours(minimumAgeHours);

long count = ticketRepository.countByAssignedToIsNullAndStatusAndCreatedAtBefore(
        TicketStatus.NEW,
        cutoff
);

```





Транзакційна межа проходить на рівні сервісу. Для читальних методів використовується `@Transactional(readOnly = true)`.


## JobDetail, тригери та параметри


Клас `QuartzJobsConfig` оголошує JobDetail і тригери як Spring-біни. Кожне завдання та кожен тригер мають окрему назву й групу. Cron-тригери посилаються на відповідний JobDetail через `forJob(...)`.


Завдання нагадування має стандартне значення віку тікета — 24 години:


Java






```
.usingJobData("minimumAgeHours", 24)

```





Для нього визначено два тригери: щоденний залишає значення 24, а щотижневий встановлює 72 години:


Java






```
.usingJobData("minimumAgeHours", 72)

```





Quartz об’єднує `JobDataMap` завдання і тригера. Якщо однаковий ключ є в обох мапах, значення з тригера має пріоритет. Решта значень JobDetail зберігається. Якщо `minimumAgeHours` відсутній, Job використовує задокументоване значення за замовчуванням — 24; некоректне значення призводить до явної помилки.


Cron-вираз, наприклад `0 0 9 * * ?`, задає запуск щодня о 09:00. У цій конфігурації тригери використовують часовий пояс GMT, щоб розклад не залежав від часового поясу сервера.


Для кожного тригера визначено поведінку на випадок пропущеного запуску — `withMisfireHandlingInstructionDoNothing()`. Це означає, що Quartz не запускає пропущений запуск одразу, а чекає наступного часу за розкладом.


## Повторні запуски й обробка помилок


Обидва завдання лише читають дані й записують результат у лог. Повторний запуск звіту або перевірки з тими самими даними не змінює стан тікетів. Це робить таку логіку безпечною для повторного виконання.


Для `UnassignedTicketReminderJob` використовується `@DisallowConcurrentExecution`, щоб два екземпляри цього самого завдання з однаковим JobKey не виконувалися одночасно.


Якщо сервіс викидає виняток, Job фіксує його в журналі й передає Quartz `JobExecutionException` із `refireImmediately=false`. Отже, негайної нескінченної серії повторів не виникає: планувальник чекає наступного запуску за розкладом.


Нагадування в поточній реалізації записується в лог, а не надсилається електронною поштою: інтеграція з email-сервісом не входить до описаних змін.


## Тестування


Тестами передбачено перевірити:



- назви та групи завдань і тригерів, а також зв’язок тригерів із JobDetail;

- наявність двох тригерів у завдання нагадування;

- значення за замовчуванням і пріоритет параметра тригера в `JobDataMap`;

- обробку відсутнього або некоректного параметра;

- часовий пояс Cron-тригерів і fallback до GMT для невідомого ідентифікатора;

- misfire-інструкцію та заборону паралельного запуску;

- повторний виклик сервісу без зміни даних;

- поведінку при помилці — без негайного повторного запуску.
